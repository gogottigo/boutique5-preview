# BOUTIQUE 5 — аудит перед передачей разработчику

Дата аудита: 22 октября 2026 г.  
Объём: статическая проверка исходников, данных, маршрутов, сборки и конфигурации. Исходный код, зависимости и конфигурация в рамках аудита не редактировались. Визуальную проверку в браузере и проверку браузерной консоли провести не удалось: в окружении нет установленного браузера или Playwright/Puppeteer.

## Краткое резюме состояния проекта

Проект — оформленный демонстрационный магазин на Astro 5 и React 19 с локальной статической сборкой. В нём есть главная страница, журнальный раздел, каталоги, товары, бренды, контакты, помощь, доставка, корзина и Mega Menu. Публичные маршруты генерируются заранее; базовый путь GitHub Pages настроен как `/boutique5-preview`, для большинства внутренних ссылок используется helper `withBase()`.

Это **визуальный frontend-прототип, а не готовый магазин для реальных заказов**. Товарный каталог содержит 8 демонстрационных записей. Корзина и избранное хранятся только в `localStorage`; оформление заказа, чат, вход и отправка форм не подключены к серверу. Это в основном явно обозначено интерфейсом, но некоторые надписи — например «На связи» и «В наличии» — могут восприниматься как реальные статусы.

Сборка `npm run build` прошла успешно: Astro сгенерировал 60 страниц. При этом проверка содержимого собранных HTML обнаружила важное расхождение: страницы catch-all маршрута, включая каталог, товар и `/help/`, отдают серверный HTML главной страницы до клиентской гидрации. Это требует исправления до SEO-проверки и профессиональной передачи.

**Общая оценка:** хорошая демонстрационная основа; до передачи backend-разработчику нужны стабилизация SSR-маршрутов, фиксация API-границы и документация; до реального запуска нужны backend-контракты и серверная логика заказа, цены, наличия и пользователя.

Astro сгенерировал **60 HTML-страниц**:

|---|---|
| `/` | `src/pages/index.astro` |
| `/journal/` | `src/pages/journal/index.astro` |
| `/journal/osenniy-garderob/`, `/journal/iskusstvo-mnogosloynosti/`, `/journal/pyat-sochetaniy-na-kazhdyy-den/`, `/journal/trikotazh-osnova-garderoba/`, `/journal/smart-casual-ofis-vyhodnye/` | Динамический статический маршрут `src/pages/journal/[slug].astro`, 5 публикаций. |

| `/product/[slug]/` | 8 статических страниц из `products`: coat, knit, shirt, jacket, trousers, shoes, overshirt, bag. |

Подкатегории открываются не как отдельные HTML-маршруты, а как query-параметры каталога. Для неизвестных URL отдельный проектный 404-маршрут не обнаружен; публикация зависит от стандартного 404 GitHub Pages.

`base: '/boutique5-preview'` задан в `astro.config.mjs:5–9`. `withBase()` добавляет префикс и не добавляет его повторно; большинство внутренних ссылок и локальных картинок используют helper. Внешние Unsplash URL, `tel:` и якоря не требуют префикса. Однако SSR-проблема ниже означает, что наличие правильного URL ещё не гарантирует правильный HTML страницы до выполнения JS.

GitHub Actions настроен на `push` в `main`, ручной запуск, с `actions/checkout@v4`, `withastro/action@v6` и `actions/deploy-pages@v5`. После проверки workflow нужно также убедиться, что в настройках репозитория Pages источником выбран GitHub Actions.

## Функциональность, которая действительно работает

- **Навигация:** клиентский роутер обновляет history через `pushState`, обрабатывает `popstate`; helper путей учитывает базовый URL.
- **Mega Menu:** категории берутся из общих деревьев; есть вложенные категории, мобильное раскрытие колонок, закрытие по Escape и клику вне меню.
- **Каталог:** локальная фильтрация по категории, размеру, цвету и цене; категории сопоставляются по `categoryPath` и разделу. Категории одежды/обуви/аксессуаров имеют общий источник данных с меню.
- **Каталоги разделов:** локальные фильтры категории, размера, бренда, sale-группы, сортировка и LoadMore. Параметры части фильтров синхронизируются с URL.
- **Поиск:** поиск по названию товара через параметр `q`; результаты открываются в `/catalog/`.
- **Товар:** отображаются демонстрационные варианты цвета и размеров; размер обязателен до добавления в корзину.
- **Избранное:** переключение работает на фронтенде, состояние хранится в `localStorage`, доступ к списку открывается через `/catalog?favorites=1`.
- **Корзина:** добавление с учётом товара, размера и цвета; изменение количества, удаление и сумма работают в браузере и переживают перезагрузку благодаря `localStorage`.
- **Журнал:** 5 статических публикаций, страницы статей, хлебные крошки, локальные фотографии, подборки товаров из локального массива.
- **Плавающий чат:** кнопка показывается на каталогах и товарах, окно открывается/закрывается и принимает локальный текст.
- **Формы:** встроенная HTML-валидация контактов и email-поля рассылки работает в браузере. Интерфейс сообщает, что данные не отправляются.
- **Адаптивность и accessibility:** имеются мобильные media queries, focus-visible, подписи форм, aria-label, alt у товарных и редакционных изображений, reduced-motion правила.

Это проверено по исходникам и статической сборке. Полный интерактивный сценарий в браузере не запускался.

## Демонстрационные функции и mock-данные

Все данные в `src/data/store.js` хранятся в JS-массиве. API-вызовов в `src` не найдено. В проекте нет backend-кода и API-контракта; аудит не делает предположений об их устройстве.

| Область | Фактическое поведение сейчас |
|---|---|
| Товары, бренды, цены, скидки | 8 статических товаров и 34 названия брендов. Скидки заданы полями в mock-объектах; наличие, цена и ассортимент сервером не подтверждаются. Большинство из 39 пунктов категорий не имеют демонстрационных товаров — пустое состояние ожидаемо. |
| Поиск и фильтры | Клиентская фильтрация локального массива; сеть не запрашивается. Поиск учитывает только `name`, не бренд и описание. |
| Варианты товара | Размер и цвет меняются в React state; наличие конкретной пары размер/цвет не проверяется. Текст «В наличии» на карточке товара демонстрационный. |
| Избранное | Массив ID в `localStorage` (`b5-favs`), без аккаунта и синхронизации устройств. |
| Корзина | Snapshot товара, цены, размера и цвета в `localStorage` (`b5-cart`). Цена и итог не перепроверяются сервером. |
| Оформление заказа | Кнопка «Перейти к оформлению» переводит в экран благодарности; текст ниже поясняет, что заказ не оформлен и оплаты нет. API заказа/оплаты отсутствует. Лимит 10 единиц из информационной страницы на уровне корзины не enforced. |
| Авторизация | Нет формы/сессии; кнопка профиля показывает «Личный кабинет скоро появится». |
| Чат | Сообщения добавляются только в локальный state. «Поддержка» не получает сообщение; быстрые ответы тоже просто добавляются как сообщение посетителя. В панели есть demo-note, но статус «На связи» выглядит как реальный. |
| Контактная форма | Проверяет поля браузером, затем показывает, что отправка недоступна. Данные не уходят на сервер и не сохраняются. |
| Рассылка | Email проходит браузерную валидацию; отправки нет, UI предупреждает об этом. |
| Социальные ссылки | URL Telegram, WhatsApp, Instagram и Maps не заданы в `src/config/socialLinks.js`; Maps сейчас ведёт на внутреннюю страницу контактов. |
| Публикации | Статический примерный контент, не CMS. `JournalRail` считает запись опубликованной, если `status` отсутствует и `published !== false`. |

## Найденные ошибки и технические риски

### Высокий приоритет

1. **Catch-all выдаёт HTML главной на страницах каталога, товаров и информационных страниц.** `src/pages/[...path].astro:23–25` рендерит `<App client:load />` без `initialPath`. В `src/ui/App.jsx:127–132` серверная ветка `useState` использует `initialPath='/'`, а браузерная ветка читает `window.location.pathname`. Проверка `dist/catalog/index.html`, `dist/product/coat/index.html` и `dist/help/index.html` обнаруживает в первоначальном HTML `class="hero"`, тогда как нужный экран выбирается только на клиенте (`App.jsx:165–182`). Последствия: неверная статическая разметка и SEO, возможный hydration mismatch/мерцание, неработающий контент до JS. **Рекомендация:** передавать route key из `Astro.params.path` в `App initialPath`, отделить initial route от browser-only state и проверить гидрацию на production preview.

2. **Репозиторий отслеживает сгенерированные зависимости и сборку.** `git ls-files` показывает 15 994 файлов из `node_modules`, 82 файла `dist` и 6 файлов `.astro`; в корне отсутствует `.gitignore`. `node_modules` занимает около 340 MB. Сборки меняют Vite-кэш в отслеживаемом `node_modules`, генерируют diff и затрудняют review/merge. **Рекомендация:** согласовать и добавить `.gitignore`, перестать версионировать `node_modules`, `.astro` и `dist` (если команда не использует `dist` как отдельный артефакт публикации); оставить `package-lock.json`.

3. **Функции магазина не подключены к backend.** Корзина, доступность, цены, скидки, заказ, вход и чат — только mock/local state. Для демонстрации это обозначено, но эти действия нельзя считать производственными. **Рекомендация:** перед подключением запросить контракт API и обозначить все операции как demo/disabled до интеграции; не считать клиентский subtotal или цену доверенными.

### Средний приоритет

4. **Сортировка «Сначала новинки» на `/catalog/` не сортирует товары по дате.** `src/ui/App.jsx:123` обрабатывает только `low` и `high`; при `new` остаётся исходный порядок `products`. Например, дата overshirt новее первой записи coat, но порядок массива не хронологический. В `StorePages.jsx:39` для каталогов разделов уже есть сортировка по `dateAdded`. **Рекомендация:** использовать общий sort helper и одинаковую трактовку `new` на обоих типах каталога.

5. **Колёсико над горизонтальным журналом перехватывает вертикальную прокрутку.** `src/ui/JournalRail.jsx:31–35` вызывает `preventDefault()` и меняет `scrollLeft`, когда вертикальный delta больше горизонтального. Это мешает выйти из секции обычным вертикальным скроллом, хотя главная использует sticky stacking. **Рекомендация:** проверить UX на трекпаде и колёсике; оставить горизонтальную прокрутку для горизонтального delta, вертикальный жест передавать странице либо делать перехват с явным и доступным условием.

6. **SEO-метаданные статических страниц частично неверны до выполнения JS.** `Layout.astro` задаёт общий title/description; специальное описание есть только для About, Delivery и Help в catch-all, а title для категорий, товаров, брендов и контактов меняется `useEffect` в `App.jsx:142–150`. Из-за клиентского обновления поисковый бот и превью ссылки могут получить общий title. Главная и каталог имеют одинаковый общий description. **Рекомендация:** генерировать title/description в Astro frontmatter по маршруту и данным, canonical строить только после подтверждения канонического домена.

7. **Компонентная граница перегружена.** `src/ui/App.jsx` отвечает за роутер, Header/Footer, домашнюю страницу, каталог, товар, cart state и persisted state; ряд компонентов записан одной JSX-строкой. `FilterPanel` для `/catalog` и общий `FilterPanel` в `StorePages.jsx` имеют разные наборы полей. Это усложняет сопровождение и тестирование. **Рекомендация:** выделять страницы и сервисы постепенно, не меняя текущий UI; вынести storage/API adapter и общие контракты товара.

8. **Стили накоплены как каскад overrides.** `src/styles/global.css` — 449 строк, максимальная длина строки около 12,4 тыс. символов. Базовые правила старого layout находятся в начале, последующие правила Header/домашней страницы и media queries переопределяют их. Это увеличивает риск регрессии при правке брейкпоинтов. **Рекомендация:** позже форматировать CSS и группировать по компонентам/страницам, сначала добавить визуальные проверки ключевых viewport.

9. **Несколько статусов выглядят реальными, хотя являются mock.** `src/ui/SupportChat.jsx:59–60` показывает «На связи»; `src/ui/App.jsx:124` показывает «В наличии». Рядом есть пояснения о демонстрационных данных, но эти формулировки могут быть замечены отдельно от пояснений. **Рекомендация:** перед клиентской демонстрацией сделать demo-состояния визуально однозначными или связать с подтверждённым API.

10. **Клиентская корзина не ограничивает количество 10 единицами.** Информационная страница содержит это условие, но `add`/`change` в `src/ui/App.jsx:161–163, 125` допускают любое количество. **Рекомендация:** если ограничение актуально в договоре и подтверждено backend, применить его на сервере и отразить корректно в UI.

11. **Не задано состояние 404 внутри React, неизвестная SPA-страница становится Home.** В `src/ui/App.jsx:182` любой нераспознанный route отображает главную. В статической публикации неизвестный URL обычно не попадает в этот код, но ошибочная внутренняя SPA-ссылка будет маскироваться. **Рекомендация:** добавить явный NotFound-компонент и статическую 404-страницу для GitHub Pages.

### Низкий приоритет

12. **В `public/` находятся Windows `Zone.Identifier` файлы**, например `public/images/boots.jpg:Zone.Identifier` и `public/videos/Homepage_Video_Background.mp4:Zone.Identifier`; Astro копирует их в `dist`. Это служебные метаданные и не используются UI. **Рекомендация:** удалить после отдельного согласования чистки и исключить их из репозитория.

13. **Старый логотип `public/images/BoutiqueN5_logo.png` (около 1,1 MB) не является активным логотипом** — Header использует `BoutiqueN5_OG_logo.jpg`. Удалять без проверки дальнейших ссылок не нужно; можно проверить перед поставкой.

## Проблемы адаптивности и визуальной целостности

- Адаптивные правила присутствуют для mobile/tablet/desktop, в том числе отдельные правила для меню, каталогов, журнала, категорий, товара и чата. Без реального браузерного прогона нельзя подтвердить отсутствие наложений или горизонтального overflow на всех страницах.
- На desktop главные секции используют sticky stacking (`global.css:376–394`), на mobile эффект отключён. Вместе с wheel-перехватом журнала это требует проверки вертикальной прокрутки и достижения footer.
- `global.css` содержит как старую базовую разметку, так и поздние overrides. Найдены повторные определения `.header`, `.header-main`, `.header-icon-btn` и селекторов главной в разных контекстах/media queries. Часть повторов ожидаема, но каскад трудно безопасно менять.
- Товарные изображения загружаются с Unsplash через прямые URL в `src/data/store.js:1–13`; fallback hero тоже удалённый URL (`src/ui/App.jsx:19,70`). ## План интеграции с существующим backend

API-контракт и серверные исходники не предоставлены, поэтому ниже описаны только зоны ответственности — конкретные URL, методы авторизации и payload нужно согласовать с backend-командой.

1. **Согласовать контракт и источники истины.** Получить схемы товара, вариантов, цены/старой цены, остатков, бренда/категорий, корзины гостя/пользователя, ошибок и пагинации. Зафиксировать, какие поля и статусы приходят от backend. Скидка и наличие должны быть авторитетными на сервере.
2. **Добавить API boundary.** Создать клиент/репозитории для каталога, товара, корзины, пользователя, избранного, заказов, контактов, рассылки и поддержки. Компоненты не должны напрямую обращаться к `fetch`; определить нормализацию DTO в модель UI, обработку отмены, timeout и ошибок.
3. **Перевести каталог и товары на серверные данные.** Согласовать параметры поиска, категории, бренда, размера, цвета, цены, сортировки и пагинации. Добавить состояния загрузки, ошибки, пустой выдачи и повторной попытки. Проверить category IDs и пути, не использовать display label как API ID.
4. **Сделать сервер авторитетным по вариантам и цене.** При выборе размера/цвета загружать реальные доступные комбинации и остатки. Корзина должна отправлять product/variant identifiers и quantity; сервер повторно рассчитывает цену, скидку, доставку и итог.
5. **Подключить корзину и оформление.** Определить guest-cart/session механику, merge после входа, ограничения количества, идемпотентность создания заказа, статусы, способы оплаты и обработку отказов. Текущий экран благодарности заменить состояниями реального заказа только после подтверждения backend-контракта.
6. **Подключить авторизацию и избранное.** Согласовать session/cookie/OAuth подход. Не хранить секреты и авторизационные токены в `localStorage` без отдельного решения по безопасности. Для гостевого избранного согласовать merge с аккаунтом.
7. **Подключить формы и поддержку.** Контактная форма — first-party endpoint, серверная валидация и лимиты; рассылка — подтверждённый провайдер и согласие; чат — реальный transport/оператор или оставить ясно маркированную демо-версию. Не использовать сторонние endpoint без утверждения.
8. **Сохранить UX-статусы.** Для каждого запроса добавить loading/error/retry/success и защиту от двойного submit. Убрать статичные «На связи»/«В наличии» либо получать их из API.
9. **Настроить тестовые среды и наблюдаемость.** Попросить backend sandbox, fixture accounts, seed data и контрактные примеры. Добавить тесты критических сценариев, проверить CORS, cookies, privacy, логи и ошибки. Не добавлять API host/секреты в репозиторий; определить публичную конфигурацию окружения для Astro.
